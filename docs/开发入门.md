## 一、技术栈：现在用的是什么

| 项目 | 是什么 | 打个比方 |
|------|--------|----------|
| **Godot 4.7.2** | 游戏引擎，负责画面、物理、声音、界面 | 一个全能的「游戏工厂」，原材料进去、游戏出来 |
| **GDScript** | 写游戏逻辑的编程语言 | 给工厂里的机器下指令的「说明书语言」 |
| **Git + GitHub** | 版本管理 | 游戏的「存档 + 云备份」，改坏了能退回 |
| **macOS + Godot 编辑器** | 开发环境 | 您试玩时看的窗口就是它 |

关键一点：**Godot 的项目文件全是纯文本**（`.tscn` 场景、`.gd` 脚本、`.godot` 配置）。所以 AI 可以直接写文件来搭游戏，王总只要在 Godot 里点运行、试玩、反馈。这也是当初从 Unity 换到 Godot 的核心原因——Unity 的场景是二进制文件，AI 写不了。

## 二、Godot 的三个核心概念（看懂这三个就懂一半了）

1. **节点（Node）= 一块乐高积木**
   每块积木只干一件事：相机管看、灯光管照亮、碰撞体管「撞不撞得到」、模型管「长什么样」。

2. **场景（Scene，`.tscn` 文件）= 拼好的乐高模型**
   一个场景就是一堆节点按树状结构拼起来，外加每个节点的参数。写在文本文件里，可以直接打开看。

3. **脚本（`.gd` 文件）= 贴在积木上的行为说明书**
   比如贴在「玩家」这块积木上的脚本写着：按 W 往前走、按空格跳、动鼠标转视角。

`project.godot` 则是总配置，它指定了**游戏从哪个场景启动**——目前是 `scenes/main.tscn`。

## 三、当前游戏是怎么实现的（一条完整链路）

### 1. 启动：`project.godot` → `main.tscn`

### 2. 主场景 `game/scenes/main.tscn` —— 一个 30×30 米的「空房间」

里面就这些节点：

| 节点 | 作用 |
|------|------|
| `WorldEnvironment` | 天空和整体光照氛围 |
| `DirectionalLight3D` | 太阳光，带阴影 |
| `Ground` | 地面：一个 30×1×30 米的绿色方块 |
| `WallNorth/South/East/West` | 四面墙，灰色方块，把场地围起来 |
| `Player` | 玩家，从另一个场景「实例化」进来 |

您可能会问：地面和墙的「模型文件」在哪？**其实没有模型文件**。它们是引擎自带的基础几何体（方块），尺寸和颜色直接写在 `.tscn` 文本里，比如地面大概长这样：

```
[sub_resource type="BoxShape3D" id="GroundShape"]   ← 碰撞体：看不见，负责"撞得到"
size = Vector3(30, 1, 30)

[sub_resource type="BoxMesh" id="GroundMesh"]        ← 网格：看得见的外形
size = Vector3(30, 1, 30)

[sub_resource type="StandardMaterial3D" id="GroundMat"]
albedo_color = Color(0.42, 0.52, 0.42, 1)           ← 颜色：草绿色
```

这里有个新手一定要知道的概念：**「看得见的形状」和「撞得到的形状」是两套东西**。

- **网格（Mesh）**：画面上看到的样子
- **碰撞体（CollisionShape）**：物理引擎计算撞不撞的东西，玩家看不见

现在两者都是方块、尺寸一致，所以看起来「所见即所撞」。以后做复杂模型（比如一棵树），外形可以很精细，碰撞体可以简单粗暴，这是游戏开发的常规做法。

### 3. 玩家场景 `game/scenes/player/player.tscn`

| 节点 | 作用 |
|------|------|
| `Player`（CharacterBody3D） | 玩家本体，能移动、会被墙挡住 |
| `CollisionShape3D` | 一个 1.8 米高的胶囊形碰撞体（人形简化） |
| `Head` | 头部位置，离地 1.6 米（正常人身高） |
| `Camera3D` | 第一人称相机，您看到的画面就是它拍的 |

玩家**没有身体模型**——第一人称游戏里低头看不到自己，没必要做，省性能。

### 4. 核心脚本（这才是「游戏灵魂」）

| 脚本 | 干什么 |
|------|--------|
| `game/scripts/player/player_controller.gd` | **玩家控制器**：重力下坠、WASD 移动、空格跳、鼠标转视角、Esc 释放鼠标、点窗口重新锁定鼠标 |
| `game/scripts/core/game_constants.gd` | **数值表**：重力 24、移动速度 6 米/秒、跳跃初速度 8、鼠标灵敏度、生命 100、能量 100……以后调手感只改这里 |
| `game/scripts/core/input_setup.gd` | **按键登记**：把 W/S/A/D/空格/鼠标左键绑定成 6 个「动作名」，脚本里用动作名而不是直接认按键，以后改键位很方便 |

`player_controller.gd` 里有两类函数值得知道：

- `_ready()`：游戏开始时执行一次（登记按键、锁定鼠标）
- `_physics_process(delta)`：**每秒执行 60 次**，每帧算一次「重力往下拉多少、按键往哪走多少」，这就是游戏「动起来」的原理

顺带说个细节：脚本里判断了「如果不是无界面模式才锁鼠标」，这样自动化测试跑的时候不会把鼠标抢走。

## 四、建模文件到底在哪？——目前：还没有

这是新手最容易困惑的点，这里直说：

- 当前场上所有东西 = **引擎自带的方块 + 纯色材质**，没有任何 `.glb`、`.obj`、`.fbx` 模型文件
- 也没有贴图、没有音效、没有动画——因为**原型的逻辑还没做完，美术是后面的事**

以后要加真模型时，流程是：

1. 用 Blender（免费）或购买/下载现成模型，导出成 **`.glb` 格式**（Godot 最推荐的格式）
2. 放进项目里的素材目录（比如 `game/assets/models/`，目前还没建）
3. 在 Godot 里打开项目，引擎会**自动导入**它
4. 把模型节点挂到场景里，再单独配一个碰撞体

所以「建模文件在哪里」目前的答案是：**在 `.tscn` 文本里，是引擎生成的方块，没有独立文件**。等做到关卡美术阶段，才会有真正的模型文件目录。

## 五、文件地图（一张表看懂整个项目）

```
game/
├── project.godot          ← 总配置，指定启动场景
├── run.sh                 ← 运行游戏
├── test.sh                ← 一键跑自动化测试
├── scenes/
│   ├── main.tscn          ← 主场景：场地 + 玩家
│   └── player/
│       └── player.tscn    ← 玩家场景：碰撞体 + 相机
├── scripts/
│   ├── core/
│   │   ├── game_constants.gd  ← 所有数值
│   │   └── input_setup.gd     ← 按键绑定
│   └── player/
│       └── player_controller.gd ← 第一人称移动逻辑
├── tests/                 ← 5 组自动化测试
└── .godot/                ← 引擎自动生成的缓存，已排除出版本库，别管它
```

**关于 `tests/`**：这是给开发上的「保险」。每次改完代码跑一下 `test.sh`，它会自动检查：场地结构对不对、玩家有没有相机、按键绑定对不对、数值有没有被误改、游戏能不能正常加载。最近还加了一道防线——就算引擎「假装成功」，脚本也会检查输出里有没有错误字样，防止「假绿」（测试显示通过、其实有错）。这样改代码不容易把已经好的东西改坏。

## 六、怎么运行

| 想干嘛 | 怎么做 |
|--------|--------|
| 玩/试玩 | 终端执行 `game/run.sh`，或 Godot 编辑器里按 F5 |
| 改数值试手感 | 改 `game_constants.gd` 里的数字，重开即可 |
| 看场景长什么样 | 用 Godot 编辑器打开 `game/` 文件夹，双击 `.tscn`，能可视化看到节点树和场地 |
| 跑自动化测试 | `game/test.sh` |

## 七、名词小词典

| 名词 | 大白话解释 |
|------|-----------|
| 引擎 | 做游戏的软件平台，Godot 就是 |
| 节点 Node | 游戏里的一块积木，只干一件事 |
| 场景 Scene | 拼好的一堆节点，存成 `.tscn` 文件 |
| 脚本 Script | 贴在节点上的行为说明书，存成 `.gd` 文件 |
| 网格 Mesh | 画面上看到的形状 |
| 碰撞体 CollisionShape | 物理上「撞得到」的形状，看不见 |
| 实例化 | 把一个做好的场景「复制」一份放进另一个场景，改原件所有副本一起变 |
| 物理解算 | 引擎每秒 60 次计算「谁碰到谁、谁该被挡住」 |
| 无界面模式（headless） | 不开窗口跑游戏，专门用来跑自动化测试 |
| 假绿 | 测试显示通过，其实有错误没被发现 |

## 八、总结一句

**现在的游戏 = 「一个能走能跳的第一人称摄像头，站在一个 30 米见方的空房间里」**，全部由 Godot 自带方块、文本场景文件和三个核心脚本实现，还没有任何美术素材。

下一步做投掷时，会新增的也是同样的套路：一个「筷子」场景（模型 + 碰撞体 + 飞行脚本）、一个「靶子」场景（模型 + 血量脚本）、以及武器管理器。本质上是同一套东西的复制粘贴和扩展。
